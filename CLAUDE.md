# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Space Invaders on FPGA — heterogeneous system: game logic on ARM HPS (C99), video output via FPGA PL. **Primary target: Xilinx Zynq-7000 (Digilent Zybo Z7-20), HDMI out via AXI VDMA + rgb2dvi**, built with Vivado 2025.2 bare-metal (Vitis). The PL is a stock IP pipeline (no custom HDL) generated by `vivado/build_hdmi.tcl` — see `vivado/LEIAME.txt`.

Original spec (`space_invaders_fpga_spec.md`) describes a custom VGA design with a `CTRL_REG` and a `hw/` VHDL folder. That design is **superseded** by the Vivado VDMA flow and the `hw/` folder does not exist — treat the spec as historical context only.

## Build Commands

### Software (ARM — bare-metal, Vitis 2025.2)

Primary flow: import `sw/` into a **Vitis standalone Application Component**
(BSP from the Vivado-exported `.xsa`). The Vitis BSP supplies startup
(`boot.S`/crt0) and `lscript.ld` — do NOT add custom ones. Full steps: `docs/VITIS.md`.

- Import only `sw/*.c|*.h` and `sw/assets/*`. Exclude `sw/host/`, `legacy-gcc/`.
- HW layer (`framebuffer.c`, `timer.c`, `input.c`) uses BSP headers:
  `xil_io.h`, `xil_cache.h`, `xtime_l.h`, `sleep.h`.
- `fb_swap()` MUST `Xil_DCacheFlushRange()` the rendered buffer (DDR cacheable).

Host dev build (PC, SDL2, no board): `make -f Makefile.host`.
Legacy raw `arm-none-eabi-gcc` build (crt0/linker/Makefile): `legacy-gcc/`.

### Hardware (FPGA — Vivado 2025.2, Zybo Z7-20)

No custom HDL — the PL is a Block Design of stock IP built by a TCL script.

1. In `vivado/`, clone the two Digilent deps (`vivado-boards`, `Zybo-Z7-20-HDMI`) — see `vivado/LEIAME.txt`.
2. Vivado TCL Console: `cd {…/vivado}` then `source build_hdmi.tcl` → builds the Block Design.
3. `Generate Bitstream` → `Export Hardware (Include bitstream)` → `.xsa` for Vitis.

Pin constraints: `vivado/hdmi.xdc` (HDMI TX differential pairs). The original spec's `vga_sync.vhd`/ModelSim flow does not apply to this VDMA design.

## Architecture

### HW/SW Split

```
ARM PS (sw/)          ←→ DDR framebuffers (32 bpp) ←→   FPGA PL (Vivado IP)
game logic                AXI HP0 (VDMA reads DDR)        AXI VDMA (MM2S)
input (AXI GPIO btns)     AXI GP0 (VDMA ctrl, GPIO)       → Subset Conv → VTC
                                                          → AXI4S-to-Vid → rgb2dvi → HDMI
```

### Memory Map

| Region | Address | Size |
|--------|---------|------|
| Framebuffer 0 (XRGB8888) | `0x20000000` | 1.2 MB (640×480×4) |
| Framebuffer 1 (XRGB8888) | `0x2012C000` | 1.2 MB |
| AXI VDMA (S_AXI_LITE) | `0x43000000` | `XPAR_AXI_VDMA_0_BASEADDR` |
| AXI GPIO (buttons) | `0x41200000` | 4 btns, all inputs |

**No `CTRL_REG`.** Double buffer + vsync are done by the AXI VDMA in *park* mode: `fb_swap()` writes the back-buffer index to `PARK_PTR_REG[4:0]` and polls the frame-done flag (`MM2S_VDMASR` bit 12) as vsync. Addresses are tool-assigned — verify against the Vivado Address Editor / `xparameters.h`.

### PL Video Pipeline (Vivado IP, no `hw/` folder)

| IP | Role |
|----|------|
| `processing_system7` | ARM PS + DDR; HP0 enabled for VDMA, FCLK0 = 100 MHz |
| `axi_vdma` (MM2S) | Reads DDR frames → AXI4-Stream, 32 bpp, 2 frame stores |
| `axis_subset_converter` | 32→24 bit, remaps channels for rgb2dvi |
| `v_tc` (VTC) | 640×480@60 timing generator |
| `v_axi4s_vid_out` | AXI4-Stream → parallel video + sync |
| `rgb2dvi` (Digilent) | RGB → TMDS (HDMI TX) |
| `clk_wiz` | 25.175 MHz pixel + 125.875 MHz (5×) serial clocks |

Defined entirely in `vivado/build_hdmi.tcl`.

### Software Modules (`sw/`)

| File | Role |
|------|------|
| `framebuffer.c` | AXI VDMA setup, `put_pixel`, `fb_swap` (park-ptr swap + vsync poll); converts RGB565→XRGB8888 at the write boundary |
| `renderer.c` | `draw_rect`, `draw_char`, `draw_string`, `draw_sprite`, `clear_screen` |
| `game.c` | Global `Game` state, `game_update`, `game_render` |
| `input.c` | AXI GPIO (bare-metal); SDL on host build |
| `assets/sprites.c` | RGB565 sprite arrays |
| `assets/font8x8.c` | 8×8 bitmap font (CP437) |

### Pixel Format

**Game/renderer/sprites use RGB565 (`uint16_t`)** everywhere — `((r>>3)<<11)|((g>>2)<<5)|(b>>3)`. The DDR **framebuffer is XRGB8888 (32 bpp, `0x00RRGGBB`)** because that's what the VDMA pipeline reads. `framebuffer.c` converts RGB565↔XRGB8888 in `put_pixel`/`get_pixel`, so game code stays 16-bit. FB layout: row-major, `offset = (y*640 + x) * 4` bytes.

### Game Loop

Fixed 60 FPS delta (`1/60 s`). Sequence per frame: `input_poll → game_update → game_render → fb_swap`. `fb_swap` flushes the back buffer's D-cache (DDR is cacheable), moves the VDMA park pointer to it, then busy-waits on the VDMA frame-done flag before continuing.

### Key Game Constants

- Player speed: 2 px/frame; bullet: 4 px/frame up; enemy bullet: 3 px/frame down
- Fleet step: 2 px, interval 0.5 s initial; interval shrinks 0.008 s per kill (min 0.05 s)
- Bunker cell: 3×3 px; grid 12×8 cells = 36×24 px total
- Collision: AABB in pixel coords

## Development Phases

1. Build PL with `vivado/build_hdmi.tcl` → bitstream → `.xsa`. Sanity-check HDMI with a solid-color DDR fill.
2. Vitis: standalone platform (BSP) from `.xsa` + application (`docs/VITIS.md`).
3. Develop `framebuffer.c`/`renderer.c` logic on host PC first (SDL, `Makefile.host`).
4. Game logic stays decoupled from HW (RGB565, no board dependency).
5. On board: verify VDMA park-mode double-buffer swap, input latency ≤ 2 frames. If colors look wrong, fix `axis_subset_converter` `TDATA_REMAP` in the TCL (not the SW).
